# 08. Portfolio v2 実装ロードマップ

> 依存関係を考慮したフェーズ構成。各フェーズは「前のフェーズの成果物がないと着手できないもの」を後ろに置いている。
> **Phase 0 のみ、サイト実装より前に必ず完了させること。**

---

## 全体像

```
Phase 0  安全確保          ← サイト実装より前
Phase 1  情報整理          ← 本人の回答が必要。ここが律速
Phase 2  即効修正          ← 依存なし。並行可能
Phase 3  情報設計の骨格
Phase 4  デザインシステム
Phase 5  Hero / Navigation
Phase 6  Projects（一覧）
Phase 7  Project Details（Case Study）
Phase 8  About / Skills
Phase 9  Responsive / Accessibility
Phase 10 Performance / SEO
Phase 11 Final QA
```

指示された10フェーズ構成に対し、**Phase 0（安全確保）と Phase 2（即効修正）を追加**した。
理由: (a) `gin_ec` の秘密情報は実装より前に処理すべき、(b) 虚偽表示の修正は情報設計の完了を待つ必要がなく、1日で信頼性を回復できるため。

**推奨する進め方**: 1作品あたり30分、以下4項目だけ先に書く。完璧を目指さない。

## 並行実行の推奨

```
週1  │ Phase 0（安全確保）      │ Phase 1 開始（質問への回答）
週2  │ Phase 2（即効修正）      │ Phase 1 継続（Case Study 執筆）
週3  │ Phase 3 → Phase 4        │ Phase 1 継続
週4  │ Phase 5（Hero / Nav）    │ 画像素材の準備
週5  │ Phase 6（一覧）          │ Phase 7 執筆
週6  │ Phase 7（詳細）          │
週7  │ Phase 8（About/Skills）  │
週8  │ Phase 9 → 10 → 11        │
```

**期間が足りない場合の最小構成**（Phase 0 → 2 → 3 → 5 → 6 → 11）:
Hero の刷新、営業セクションの撤去、技術表記の修正、サムネイル付き一覧まで。
詳細ページは FEATURED 1件だけ作り、他は「準備中」ではなく**一覧のみの掲載**にする（空ページを作らない）。

## 授業要件に沿った開発の進め方

各 Issue について以下のサイクルを回すこと。**これ自体が授業の評価対象**になる。

```
1. GitHub Issue を作成（07_implementation_backlog.md の内容をそのまま貼る）
2. ブランチを切る（例: feat/hero-identity, fix/tech-tags）
3. コミット（Conventional Commits。現行の履歴も準拠している）
4. Pull Request を作成（何を・なぜ・どう確認したかを記述）
5. CI が緑であることを確認
6. Merge（main を常に正常な状態に保つ）
```

現在 Issue 0件 / PR 0件 / ブランチ main のみ。**v2 の開発をすべてこのサイクルで行えば、それだけで「GitHub / Engineering Presentation」の採点（現在10点中2点）が大きく改善する。**
