### 4-2. 効果数値の根拠

| 表示 | 根拠 |
|---|---|
| 制作工数 -70% | **なし**（実測・比較対象・計測方法いずれも不明） |
| 営業工数 -40% | **なし** |

これらは実在ユーザーのいないデモアプリの数値であり、**検証不可能な主張**。営業LPとしてはよくある表現だが、**就活ポートフォリオでは「盛り」と判断されるリスク**が高い。

**対応方針**: 削除するか、「想定効果」と明示するか、実測できるもの（例: 「手作業なら30分の見積作成が3クリックで完了」のような操作数ベース）に置き換える。

### 4-3. 「制作物」ではなく「思考」が見せられているか

**見せられていない。** これが現行ポートフォリオの**構造的な最大欠陥**であり、Portfolio v2 の中心的な差別化要素にすべき点。

現在のサイトが答えているのは「**何ができるか（What）**」だけ。
採用担当者が知りたいのは「**なぜそうしたか（Why）**」と「**どう解決したか（How）**」。

| 問い | 現状 | v2で置く場所 |
|---|---|---|
| なぜ作ったか | ✗ | Case Study: Problem / Background |
| どこで詰まったか | ✗ | Case Study: Challenges |
| どう調査したか | ✗ | Case Study: Solutions（切り分けの過程） |
| どう解決したか | ✗ | Case Study: Solutions |
| なぜその設計にしたか | ✗ | Case Study: Technical Decisions |
| 何を改善したいか | ✗ | Case Study: Future Improvements |

**補足**: 現行の `Why` セクション（「業務を理解する→解くべき課題を設計する→動くものとして実装する」）は、**思考を語ろうとした形跡**として質が高い。ただし抽象論に留まり、具体的な作品と結びついていない。v2 ではこれを各 Case Study の中で**具体例として証明する**構成にすると活きる。

## 5. Case Study 情報モデルの評価

指示された情報モデルを、この学生の実情に照らして評価する。

| 項目 | 採用 | 備考 |
|---|---|---|
| Project Summary | ◎ 必須 | 3行。何を・誰のために・いつ |
| Problem / Background | ◎ 必須 | **最重要**。学校課題なら「課題として与えられた」でも良いが、その中で自分が設定した問題を書く |
| Goal | ◎ 必須 | Problem と統合して1ブロックでも可 |
| Role | ◎ 必須 | 個人/チーム、チームなら人数と自分の担当。**おうちかふぇ（4人）で特に重要** |
| Tech Stack | ◎ 必須 | **実装と一致させること**（現行の最大の問題） |
| Architecture | ○ 推奨 | 図は1枚で十分。作れない作品は構成の箇条書きでも可 |
| Key Features | ○ 推奨 | 3〜5個に絞る。全機能列挙は不要 |
| **Technical Decisions** | ◎ 必須 | **最も差がつく項目**。「なぜFastAPI / PostgreSQL / SSE / Vercel か」。**現時点で本人の回答が必要（TODO多数）** |
| **Challenges** | ◎ 必須 | 「動いた」より「詰まった」の方が評価される |
| **Solutions** | ◎ 必須 | 原因の切り分け方を書く。**ここが技術面接そのもの** |
| Security | ○ 作品による | 認証/認可/入力検証/Secret管理/SQLi/XSS/CSRF/CORS。**該当する対策のみ書く。やっていないものを書かない** |
| Testing | △ 該当作品のみ | 現状テストがあるのは `Attendance-Tracking-App`（vitest 6本 + Playwright 2本）のみ。**ない作品に「テスト: なし」と書くのは誠実で問題ない** |
| Deployment | ○ 推奨 | Vercel / Render / Firebase 等、作品ごとに異なるので価値がある |
| CI/CD | △ 該当作品のみ | GitHub Actions を組んだ作品のみ |
| GitHub / Live Demo | ◎ 必須 | — |
| Screenshots / Demo動画 | ◎ 必須 | **現在0枚。最優先で用意すべき素材** |
| What I Learned | ◎ 必須 | 3行で十分 |
| Future Improvements | ○ 推奨 | 「今なら何を変えるか」は授業要件にも合致 |

### 全項目を全作品に書く必要はない

作品を**3階層**に分け、記述量を変える。

| 階層 | 対象 | 書く項目 |
|---|---|---|
| **FEATURED**（2〜3件） | 代表作 | 全項目（Case Study フル） |
| **STANDARD**（3〜6件） | 通常掲載 | Summary / Problem / Role / Stack / Key Features / Challenges / Solutions / Links |
| **ARCHIVE**（残り） | 一覧のみ | 名前 / 一言 / 技術 / リンク |

全作品をフル Case Study にすると、書ききれずに全部が中途半端になる。
