### Q6. 「面接で説明できる」技術はどれか
以下のうち、**実際に作品で使い、仕組みを説明でき、詰まった経験がある**ものを選ぶ。

```
PHP / SQL / HTML / CSS / JavaScript / TypeScript / Python
Laravel / FastAPI / REST API / SSE
MySQL・MariaDB / PostgreSQL / Neon
```

## D. 各作品の Case Study（Phase 7 の素材・本人しか書けない）

以下は**掲載する各作品について**必要。FEATURED 作品は全項目、STANDARD は Q12〜Q14 のみでもよい。

### Q12. なぜ作ったか（Problem / Goal）
- 何がきっかけか（授業課題 / 自分の困りごと / 依頼 / 技術を試したかった）
- 何を解決しようとしたか

### Q13. どこで詰まったか / どう解決したか（Challenges / Solutions）
- 一番時間を取られた問題は何か
- **どうやって原因を切り分けたか**（ログを見た / 最小再現を作った / ドキュメントを読んだ / 切り分けの順序）
- 最終的にどう直したか

> **採用担当者が最も知りたい項目。** 「動いた」より「詰まって、調べて、直した」の方が評価される。

### Q14. なぜその技術にしたか（Technical Decisions）
作品ごとに該当するものだけ。

- なぜ FastAPI か（おうちかふぇ / ここまね）
- なぜ PostgreSQL / MySQL か
- なぜ SSE か（使っている作品がある場合）
- なぜ Vercel / Render / Azure / Firebase か
- なぜ生PHP か（おうちかふぇで Laravel を除去した経緯）
- なぜ Prisma ではなく生SQL（`pg`）にしたか（MVP 5本）

> **注意**: MVP 5本のサイト表記には現在 `Prisma` とあるが、**実装は生SQL**。この不一致の修正（ISSUE-P0-01）と合わせて、「なぜ ORM を使わなかったか」を説明できると、むしろ強い材料になる。

### Q15. チーム作品での担当範囲（Role）
おうちかふぇ（4人）・ここまね（4人）について。

- 自分の担当領域（フロント / バックエンド / DB設計 / インフラ / ML / 進行管理）
- チーム内での役割
- 他メンバーの成果と自分の成果の境界

> **これを書かないと、チーム成果を個人の成果と誤解される（または逆に、貢献が過小評価される）リスクがある。**
