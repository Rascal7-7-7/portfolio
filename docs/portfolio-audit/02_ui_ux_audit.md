### 3つの問い

**Q1. 一目でエンジニア志望だと分かるか → NO**
「業務改善 & MVP開発」「一人で対応します」「最短5日で構築」は**受注者の自己紹介**であり、就職を希望するエンジニア学生の自己紹介ではない。

**Q2. Web制作だけの学生に見えてしまわないか → YES、見えてしまう**
提示されている作品はLP生成・予約・見積・EC・案件管理という**すべて業務系Web**。技術タグも Next.js / Tailwind / PostgreSQL 系のみ。AI / セキュリティ / ネットワーク / クラウドの語が**サイト全体で0回**。

**Q3. AI / Cloud / Security / Network への志向が自然に伝わるか → NO、まったく伝わらない**
本人の関心分野（AI×セキュリティ、AI×クラウド、セキュリティ×ネットワーク）が一切可視化されていない。**現状のサイトを見た採用担当者は、この学生をWeb制作志望として分類する。**

### 演出について

現行デザインは**ネオン・過剰グラデーション・Particle・3D・Glassmorphism・Cyberpunk のいずれも使っていない**。これは正しい判断であり、Portfolio v2 でも維持すべき。
不足しているのは演出ではなく、**専門性を示す情報（分野・作品の実像・思考の記録）**。

### 3-4. 「どこをクリックすればいいのか迷う箇所」（全抽出）

1. **ファーストビューの2つのCTA**。「無料で相談する」と「MVP事例を見る」のどちらが主要動線か、視覚的な優劣はあるが**採用担当者にはどちらも押す理由がない**。「作品を見る」が主CTAであるべき。
2. **同じ文言のCTAが3箇所に出現**。「無料で相談する」が Hero(→`#contact`) / CTAセクション(→`mailto:`) / Footer(→`mailto:`) にあり、**同じラベルで遷移先が違う**（アンカー移動かメーラー起動か）。押すまで結果が分からない。
3. **「デモを見る」が5箇所**。リンクテキストだけでは、どの作品のデモか判別できない（スクリーンリーダーのリンク一覧では全て同一テキストに見える）。
4. **「設計・コードを見る」が6箇所**。5作品分＋フッターのプロフィールリンク。フッターのものだけ**個別リポジトリではなくGitHubプロフィール**に飛ぶが、同じラベル。
5. **「MVP事例を見る」が2箇所**（Hero / CTAセクション）。どちらも `#mvps` で同じだが、CTAセクションのものは**すぐ下にある作品一覧へ飛ぶだけ**で情報価値が薄い。
6. **カード全体がクリックできない**。カードは `<article>` でホバー時に背景色が変わるが、リンクはカード下部の2つのテキストリンクのみ。**ホバー反応があるのにクリックできない**ため誤操作を誘発する。
7. **「無料相談」ボタン（作品一覧の直下）**。作品を見た直後に営業CTAが挟まり、次の作品や詳細への動線を分断している。

## 4. Projectsセクション監査（最重要）

### 現在の構造

```
MVPGrid.tsx
 └── const mvps: MVPCardProps[] = [ ... 5件をコンポーネント内にハードコード ... ]
      └── grid-cols-1 / sm:2 / lg:3 で MVPCard を並べるだけ
```

### 作品数増加への耐性 — **耐えられない**

| 課題 | 内容 |
|---|---|
| **データがコンポーネント内にハードコード** | `MVPGrid.tsx` の中に配列リテラル。作品追加のたびにUIコンポーネントを編集する必要がある。データ層の分離（`content/projects/*.ts` 等）が必須 |
| **分類・絞り込みがない** | 全件フラット表示。今後「個人開発 / 学校課題 / 進級制作 / チーム制作 / AI / クラウド / セキュリティ」が混在すると、**閲覧者が目的の作品に辿り着けない** |
| **序列がない** | 5枚が等価。代表作を強調する仕組みがない |
| **詳細ページがない** | カード＝終点。Case Study を載せる場所が構造的に存在しない |
| **画像がない** | `public/` すら存在せず、視覚的な識別子がゼロ。作品が10件を超えると文字だけのカードの海になる |
| **個人/チームの区別がない** | 進級制作（4人チーム）と個人開発を同じカードで並べると、貢献範囲が誤解される |
| **期間表記の意味が変質する** | 現在「開発期間 5日」は受注リードタイムの訴求。学習成果としては「2025-10〜2026-02」のような制作時期の方が適切 |

### 改善方針（詳細は `06_information_architecture.md`）

1. **データをコンテンツ層に分離**（`content/projects/<slug>.ts` または MDX）
2. **`/projects` 一覧 + `/projects/[slug]` 詳細**の2階層化
3. **FEATURED（代表作2件）→ その他** の2段構成
4. **カテゴリタグによる絞り込み**（AI / Cloud / Security / Web / Team / 学校課題）
5. **サムネイル画像を必須項目に**

## 5. Project Card 監査

### 現在カードに載っている情報（8種）

| # | 情報 | 一覧に必要か | 判定 |
|---|---|---|---|
| 1 | 開発期間「5日」 | △ | 受注文脈の指標。制作時期に変更すべき |
| 2 | ターゲット「美容室・クリニック」 | ✗ | 詳細ページへ |
| 3 | 価値メッセージ（h3, 最大） | ✗ | **作品名より目立っているのは誤り** |
| 4 | 作品名（12px） | ✓ | **最も目立つべき情報** |
| 5 | 説明文（3行） | △ | 1〜2行に圧縮 |
| 6 | 効果バッジ「制作工数-70%」 | ✗ | **根拠のない数値。削除または実測値に置換** |
| 7 | 技術タグ | ✓ | **ただし現在は事実と不一致** |
| 8 | デモ / GitHub リンク | ✓ | — |

### 一覧に表示すべき情報（提案）

| 優先 | 情報 | 理由 |
|---|---|---|
| **必須** | サムネイル画像 | 一覧での識別子。現在ゼロ |
| **必須** | 作品名 | 記憶と質問の単位 |
| **必須** | 一言説明（1行・40字以内） | 何のアプリか |
| **必須** | 主な技術（3〜4個まで） | 技術面接官のスキャン対象 |
| **必須** | 個人 / チーム（＋人数） | 貢献範囲の誤解防止 |
| **必須** | 「詳細を見る」 | **サイト内の深掘り導線。現在存在しない** |
| 推奨 | カテゴリ（AI / Cloud / Security / Web） | 絞り込みと志向の可視化 |
| 推奨 | 制作時期 | 成長の時系列 |
| 任意 | GitHub / Live Demo | 詳細ページに集約してもよい。一覧に置くならアイコンで省スペース化 |

### 詳細ページで読むべき情報（一覧から外すもの）

- ターゲットユーザー / 想定シーン
- 機能一覧
- アーキテクチャ図
- 技術選定の理由
- 詰まった点と解決過程
- セキュリティ対策
- テスト・デプロイ・CI/CD
- 学んだこと / 今なら何を変えるか

**原則**: 一覧は「**選ぶため**」の情報、詳細は「**評価するため**」の情報。現在のカードは両者が混ざった上で、肝心の評価材料（思考の記録）がどこにもない。
