### 現時点で「AI × セキュリティ」を裏づけられる既存資産

| 資産 | 何が言えるか | 強度 |
|---|---|---|
| **ここまね（2026-project）** | ローカルLLM（Ollama / `moko-nemotron`）をアプリに組み込んだ実装。**メンタルデータを医療個人情報と同等に扱う方針**（暗号化カラム・最小取得・ログ除外）。`docs/runbooks/secret-incident-20260906.md` に**シークレット漏洩対応の手順書** | ◎ |

**不足しているもの: 「AI特有のセキュリティ問題」を実際に扱った作品が1本もない。**
Prompt Injection / Jailbreak への興味は語れるが、**証拠がない状態**。ここが埋まると、他の学生とほぼ確実に差別化できる。

### 決定: 不足を埋める1本を、MVP改修と統合する

`10` では `mvp-booking-system` を「認証・入力検証・テスト・CI を入れてセキュリティ作品にする」と決めたが、**これを AI × セキュリティのショーケースに格上げする**。

**改修後の booking-system の到達目標**

```
[AI側]
  予約の自然言語入力（「来週の火曜の午後、カットで」→ 構造化データ）を LLM で処理

[セキュリティ側]
  1. Prompt Injection 対策
     - システムプロンプトとユーザー入力の分離
     - LLM出力を信頼せず、構造化スキーマ（zod等）で検証してから DB に渡す
     - 「予約以外の指示は実行しない」制約と、その回避試行の検出・ログ記録
  2. 攻撃試行の記録と可視化
     - injection を試みた入力を記録し、管理画面で確認できる
  3. 従来のWebセキュリティ
     - 認証・権限分離・入力検証・レート制限・CSRF/XSS/SQLi 対策
  4. テストで証明
     - injection ペイロードを流して「構造化検証で弾かれる」ことをテストで示す
```

**この1本で、興味順位の1位・2位・3位・4位（デプロイ）をすべて1作品で裏づけられる。**
規模も小さく（現状5画面・33ファイル）、v2公開後の改修として現実的。**面接で最も話が伸びる作品になる。**

> 注: これは v2 公開後のタスク。公開を改修完了まで待たない。

### `oss` リポジトリの扱い（新規判断）

セキュリティが興味順位2位である以上、**責任ある開示の実績1件は掲載する価値がある**。
ただし以下を守ること。

- **公開済み・修正済みの1件（`ii-agent`）に絞る**。未公開の findings は載せない
- `targets/` のクローン（他人のOSS）は公開対象から外す
- 「脆弱性を探すワークスペース」ではなく「**責任ある開示のプロセスを実践した記録**」として提示する
- 掲載形態は **ARCHIVE または STANDARD の1エントリ**。自作コードは9ファイルなので、コード量ではなくプロセスで語る

## 2. 「実際に触れるようにできるのか」への回答

### 結論

**全作品を公開デモにする必要はないし、するべきでもない。**
採用担当者が確認したいのは「本当に作ったのか」であって「全部触れること」ではない。**無理にデプロイして壊れた状態で置く方が減点になる。**

そのうえで、**言語・構成ごとに現実的な公開方法は存在する**。以下に確定方針を示す。

### 確認手段を3段階で明示する

ポートフォリオの各作品に、確認方法のバッジを表示する。これ自体が誠実さの表明になる。

```
🟢 LIVE DEMO    公開URLでそのまま触れる
🎬 DEMO VIDEO   動画 + スクリーンショット + アーキテクチャ図
📄 CODE ONLY    コードとドキュメントのみ（理由を明記）
```

---

### 作品別の公開方針（確定）

#### 🟢 MVP 5本 — 対応不要

5本とも本番稼働中、全リンク200を実測済み。**そのまま維持**。
唯一 `mvp-booking-system` のデモ初期画面が「本日の予約 0件」で空に見えるため、**シードデータを相対日付に変更**（改修時に対応）。

#### 🟢 Attendance-Tracking-App — デモアカウントが必要

**実測で判明**: 公開URL（`attendance-tracking-app-inky.vercel.app`）は 200 で稼働しているが、**トップがログイン画面**（メールアドレス + パスワード）。採用担当者は入れない。

| 対応案 | 工数 | 推奨 |
|---|---|---|
| デモ用アカウントを作り、ポートフォリオとREADMEに ID/PW を明記 | **小** | **◎ これを採用** |
| ゲストモード（閲覧のみ）を実装 | 中 | △ |
| ログイン画面のスクショのみ | 小 | ✗ 触れないなら意味が薄い |

**決定**: デモアカウント方式。シードデータ（架空の時間割・出席記録）を入れ、**誰がログインしても同じ状態に戻るようにする**（または定期リセット）。実在の授業名・個人名は使わない。

#### 🟢 it-study — デプロイする。ただし画像は載せない

**重要な発見**: **リポジトリに問題画像は1枚も入っていない**（`git ls-files` で png/jpg が **0件**）。ローカルの `public/question-assets/`（**1.6GB**）は gitignore 済み。

つまり **#6 の著作権懸念は、リポジトリ公開については既に回避されている。**
判断が必要なのは「**公開デモで問題画像を表示するか**」だけ。

そして技術的にも答えは決まっている:

> **1.6GB の画像は Vercel にデプロイできない。** サイズ的にそもそも載らない。

| 選択肢 | 判断 |
|---|---|
| A. 画像なしでデプロイ（アプリの機能・UI・採点・可視化を見せる） | **◎ 採用** |
| B. 自作のサンプル問題を数問だけ用意して表示 | ○ 併用推奨。「問題が表示される画面」を見せられる |
| C. IPA の問題画像をそのまま公開サイトに載せる | **✗ 採用しない**（サイズ的に不可、かつ権利判断を要する） |

**決定**: **A + B**。公開デモは自作サンプル問題（10問程度を自分で作成）で動かす。README に「学習用の公式問題データはローカルで取得する構成」と明記し、取得スクリプトを提供する。

> IPA公開問題の二次利用条件については、**IPAの公式サイトの利用条件を本人が一次情報で確認すること**。私の推測で可否を断定しない。ただし上記の A + B 構成なら、**その判断を待たずに公開できる**。

**追加作業**: Neon（PostgreSQL）への接続と Vercel デプロイ。`vercel.json` / Dockerfile は現在なし。工数は中。

#### 🎬 おうちかふぇ（gin_ec） — 動画 + スクショを基本に

**構成**: 生PHP 8.2 + MySQL 8.0 + FastAPI（Python）+ 学習済みMLモデル（`cf_model.pkl` 14MB、`ncf_model.pth` 3.6MB ほか）

| 選択肢 | 内容 | 工数 | コスト | 判断 |
|---|---|---|---|---|
| A. フル公開 | PHP(Docker) + MySQL(外部) + FastAPI の3リソースを Render / Cloud Run へ | **大** | 無料枠でもスリープ・コールドスタートあり | △ 時間があれば |
| B. 部分公開 | PHPとMySQLのみ公開し、ML推薦は**事前計算済みの結果を返すモック**に差し替え | 中 | 小 | ○ 現実的な妥協点 |
| **C. 動画 + スクショ + アーキ図** | 3分のデモ動画、主要画面6〜8枚、構成図1枚 | **小** | 0 | **◎ まずこれ** |

**決定**: **C を確定。B は余力があれば。**
理由: 4言語・3プロセス構成を無料枠で安定稼働させるコストに対し、採用上の効果が見合わない。**大規模なチーム制作は、動画とアーキテクチャ図の方がむしろ伝わる。**

**必須の前提（`10` から継続）**:
- **`.env`（4.4KB）と DBダンプ3本（35MB / 18MB / 1.7MB）をリポジトリから外す** — 後述のリポジトリ整理
- デモ動画・スクショに**実データ（実メールアドレス等）を映さない**。架空のシードデータで撮影する

#### 🎬 ここまね（2026-project） — 動画 + スクショ。Flutter Web は任意

**構成**: Flutter（モバイル）+ FastAPI + Neon PostgreSQL + Redis + **ローカルGPU上の Ollama**

**実測**: `2026-project.vercel.app` は **404**。現状、外部から触れる公開デモは存在しない。

| 課題 | 内容 |
|---|---|
| モバイルアプリ | URLで触れない。`flutter build web` で Web版は作れるが、モバイル前提UIになる |
| バックエンド | Render / Fly の無料枠 + Neon（既に使用中）で公開可。工数中 |
| **AI機能** | **`moko-nemotron` はローカルGPU上で動作。クラウドでは動かない。** デモ用にホスト型API（Gemini等）へ差し替えるか、モック応答にするフラグが必要 |
| チーム・学校 | 現在進行中の進級制作。公開デモを立てるならチームと学校の合意が要る（同意済みとのことだが、公開デモは別途確認推奨） |

| 選択肢 | 工数 | 判断 |
|---|---|---|
| **A. 動画 + スクショ + アーキ図 + ADR抜粋** | 小 | **◎ 採用** |
| B. Flutter Web の読み取り専用デモ（AI部分はモック） | 中〜大 | ○ 余力があれば |
| C. フル公開 | 大 | ✗ AI部分が動かない以上、中途半端になる |

**決定**: **A を確定。**
このプロジェクトの強みは**動くアプリそのものより、574コミット・53PR・CI緑・ADR・テスト239ファイルという開発プロセス**にある。**GitHub と Case Study で語る方が価値が高い。**
デモ動画は既存の `docs/mockup/prototype.html`（全19画面）を画面収録すれば短時間で作れる。

#### 📄 OSS 責任ある開示 — コードとドキュメントのみ

デモという概念がない。**開示レポート（提出済みの1件）とプロセス文書**で見せる。

## 3. リポジトリ整理方針（本人回答4への対応）

前提: **APIキーは既に使用不可の状態** とのこと。したがって**緊急のローテーションは不要**。
残る対応は「リポジトリを公開できる状態にする」こと。

### 整理対象（実測で確認済み）

| リポジトリ | 追跡されているファイル | 対応 |
|---|---|---|
| **gin_ec** | `.env`（4.4KB・実キー入りだが失効済み） | 削除 |
| **gin_ec** | `database/exports/backup_before_optimization_*.sql`（**35MB**） | 削除 |
| **gin_ec** | `database/exports/gin_ec_full_backup_*.sql`（**18MB**） | 削除 |
| **gin_ec** | `database/exports/gin_ec_full_backup_*.sql.gz`（1.7MB） | 削除 |
| **webapp-project** | `.env.production` — **DB_HOST / DB_NAME / DB_USER が実値**（ロリポップのMySQL接続情報）。`DB_PASS` はプレースホルダで**パスワードは入っていない** | 削除 |
| 2026-project | `backend/alembic/versions/0012_user_pin_credentials.py` ほか | **対応不要**（ファイル名に credentials を含むだけのマイグレーション。秘密情報ではない） |
| その他（it-study / Attendance / portfolio-mvps / AI_Trade / discord_bot 等） | `.env.example` のみ | **対応不要**（サンプルファイル） |

**DBダンプの重要性**: `.env` より、むしろこちらが問題。
`gin_ec_full_backup` の `users` テーブルには**実メールアドレス3件（うち2件は学校ドメイン `@i-seifu.jp`）と bcrypt ハッシュ3件**が含まれる。鍵と違い、**個人情報は失効しない**。

### 整理の方法 — 2案

| 方式 | 内容 | メリット | デメリット | 推奨 |
|---|---|---|---|---|
| **A. 履歴ごと作り直す（新規リポジトリ）** | `.env` と DBダンプと `vendor/` と巨大画像を除いた状態で、**履歴なしの公開用リポジトリを新規作成**。既存 private リポジトリはそのまま保全 | 安全・確実。共同制作者の手元を壊さない | **608コミットの履歴が公開版に残らない**（＝開発プロセスを見せられない） | **○ 安全重視ならこれ** |
| **B. 履歴を書き換える（`git filter-repo`）** | `.env` とダンプを全履歴から除去し、force push | **608コミットの履歴を保ったまま公開できる** | 破壊的。全コミットハッシュが変わり、**共同制作者3名の手元のクローンが壊れる**。事前連絡が必須 | **◎ 履歴を見せたいならこれ** |

**推奨: B（`git filter-repo`）**。ただし条件付き。

理由: おうちかふぇの最大の価値は **608コミット・4人チーム** という開発プロセスそのもの。
履歴なしの新規リポジトリにすると、**ポートフォリオで一番見せたい部分が消える**。

**Bを実行する場合の手順（実行前に必ずバックアップ）**:
1. 現在のリポジトリを丸ごとバックアップ（`git clone --mirror`）
2. 共同制作者3名に事前連絡
3. `git filter-repo` で `.env` と `database/exports/` を全履歴から除去
4. `.gitignore` に追記されていることを確認
5. force push
6. GitHub の Settings からキャッシュされた古いコミットの削除をサポートに依頼（またはリポジトリ再作成）

> **この作業は破壊的です。実行するかどうかは本人の判断が必要**であり、私の側では実行しません。手順書が必要なら別途作成します。
> なお `.git` の履歴から消しても、**GitHub 側に古いコミットがキャッシュとして残る**ことがあります。鍵が失効済みである点が、ここで効いてきます。

### webapp-project の扱い

ITパスポート学習システム。it-study と内容が重複し、掲載候補からは外れている。
`.env.production` を削除するか、**リポジトリを private のままにする**（現在 private）。掲載しないなら、後者で十分。
