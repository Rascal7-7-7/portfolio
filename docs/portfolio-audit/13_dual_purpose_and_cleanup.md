# 13. 就活用と営業用の兼用可否 / リポジトリ・インフラ整理方針

> 作成日: 2026-09-11

## 1. 就活用と営業用の兼用 — 可能。ただし「1ページ」では無理

### 結論

**1つのページで両立させるのは不可能。** 目的が逆方向を向いているため、どちらの読者にも中途半端になる。
**1つのサイト・2つの入口なら成立する。** これを推奨する。

### なぜ1ページでは無理か

| 要素 | 就活で必要なもの | 営業で必要なもの |
|---|---|---|
| 主語 | **私は何を学び、どう考えるか** | **あなたの課題をどう解決するか** |
| 主要CTA | 作品を見る / GitHub | 相談する / 問い合わせ |
| 名乗り | 学生 | 事業者・受注者 |
| 作品の見せ方 | **思考の過程**（なぜ・詰まった点・解決） | **成果**（工数削減・導入効果） |
| 望ましい印象 | 伸びしろ・学習姿勢・素直さ | 実績・安心感・完成度 |
| 読了後の行動 | 面接に呼ぶ | 見積を依頼する |

現行サイトが2分テストで FAIL したのは、**採用担当者に営業文を読ませていたから**。逆に、就活向けの「学生です・学習中です」を前面に出すと、今度は取引先が不安になる。**同じ文章で両方を満たす書き方は存在しない。**

### 推奨構成: 入口分離（1リポジトリ・1デプロイ）

```
/                    就活用（デフォルト・採用担当が見る）
  Hero  : 氏名 / 学生 / NPO法人でエンジニアとして活動中 / AI×セキュリティ
  CTA   : 作品を見る・GitHub
  作品   : Case Study 重視（なぜ・詰まった点・解決）

/services            営業用（取引先にURLを直接渡す）
  Hero  : 業務改善・MVP開発
  CTA   : 相談する
  作品   : 成果重視（同じ作品データを別の切り口で表示）

共通: 作品データ（content/projects/）・デザインシステム・コンポーネント
```

**利点**: 作品データ・デザイン・デプロイが1本なので保守が二重にならない。ナビゲーションに `/services` を出さなければ、採用担当者が営業ページに当たる確率は低い。

**採用担当者が `/services` を見つけた場合**: 問題にならない。
「NPO法人でエンジニアとして活動中」「個人で受託開発の経験あり」はすでに就活側にも書く方針で、**実務経験として整合している**。むしろ強みになる。

### 兼用にあたっての注意点（3つ）

**① 新卒採用では「フリーランス継続」が懸念になり得る**
副業規定のある企業は多く、「入社後も受注を続けるのでは」と読まれると不利になる。
→ **就活側では「フリーランスエンジニア」と名乗らない。** 「学生 ／ NPO法人でエンジニアとして活動中」「受託開発の経験あり」に留める。事実は同じで、受け取られ方だけが変わる。

**② ⚠️ Vercel Hobby プランは商用利用が制限されている**
現在の Vercel アカウント（`rascaldevops-6114`）は Hobby プランと見られる。
**Hobby は非商用利用が前提**で、受注営業のためのサイトを載せると規約に触れる可能性がある。
→ **本格的に営業で使うなら Pro（有料）への変更が必要かどうか、Vercel の利用規約を本人が確認すること。** 私の側で断定はしない。
→ 当面は「実績紹介ページ」の範囲に留め、見積・決済・フォーム等の商行為を載せないのが安全。

**③ 効果数値の扱いは両方で同じ**
「制作工数 -70%」のような根拠のない数値は、**営業用でも削除する**。
就活で問題になるだけでなく、取引先に対しても、根拠を聞かれたときに答えられない主張は信用を落とす。

### 運用の選択肢

| 案 | 内容 | 推奨 |
|---|---|---|
| **A. 入口分離（`/` + `/services`）** | 上記 | **◎** |
| B. 時期で切り替え | 就活中はトップを就活用、終了後に営業用へ重心を移す | ○ シンプルだが、同時期に両方必要なら不可 |
| C. 完全分離（別ドメイン・別プロジェクト） | 屋号で本格的に営業するなら | △ 保守が2倍。現時点では過剰 |

**決定: A。** `/services` の実装は Phase 8 以降（就活側が完成してから）でよい。

## 2. リポジトリ整理 — やるべき。ただし順序が重要

### 現状（実測）

GitHub リポジトリ **38件**（public 13 / private 23 / fork 2）。

### 整理の4分類

#### ① 秘密情報・個人情報の除去（最優先）

| 対象 | 内容 | 対応 |
|---|---|---|
| **gin_ec** | `.env`（失効済みキー）+ **DBダンプ3本（35MB / 18MB / 1.7MB、実メールアドレス・bcryptハッシュ入り）** | **鍵より個人情報が問題。失効しないため最優先** |
| **webapp-project** | `.env.production`（DB_HOST / DB_NAME / DB_USER が実値。パスワードはプレースホルダ） | 削除 or private 維持 |

#### ② 削除してよいもの

| リポジトリ | 根拠 |
|---|---|
| **NOX-VELT** | **空リポジトリ**（GitHub API が "Git Repository is empty" を返す・0KB） |

#### ③ アーカイブ（GitHub の Archive 機能で read-only 化）

| リポジトリ | 根拠 |
|---|---|
| `git-practice` | Git練習用（39コミット）。残す価値はあるが現役ではない |
| `AI_prompt` / `AI_work` / `scan` / `scan-main` / `python-ocr` | 現役でない。削除せず読み取り専用に |
| `2025-php` / `java-for-school` / `web-kadai` | 授業課題。履歴として残す |

> **削除ではなくアーカイブを推奨する理由**: 授業で「GitHubで開発履歴が確認できる」ことが評価される。リポジトリ数を減らすより、**現役かどうかが一目で分かる状態**にする方が価値がある。

#### ④ MVP 5リポジトリの統合

**実測したコミット数**:

| リポジトリ | コミット数 |
|---|---|
| mvp-lp-generator | **2** |
| mvp-booking-system | **6** |
| mvp-estimate-manager | **10** |
| mvp-subscription-ec- | **5** |
| mvp-freelance-manager | **6** |
| （モノレポ portfolio-mvps） | 6 |

**どちらも履歴が薄く、統合しても失うものがほぼない。**（おうちかふぇの608コミットとは事情が違う）

**決定**: **モノレポ（`portfolio-mvps`）に一本化し、個別5リポジトリはアーカイブする。**

- ポートフォリオからのリンク先をモノレポの各ディレクトリに変更する
- `mvp-subscription-ec-`（末尾ハイフンのtypo）も自然に解消される
- **リンク切れを作らないよう、v2のリンク差し替えと同時に実施する**

### ⚠️ 順序の注意

**リポジトリ整理は Phase 2（即効修正）の後に行う。**
理由: 整理は「壊れると困る作業」であり、公開中のポートフォリオからリンクされているものを先に触ると、修正前にリンク切れが発生する。

```
Phase 2（技術タグ修正・favicon等）
  → v2 のリンク構造を確定
    → リポジトリ整理（リンク先の差し替えと同時に）
```

## 4. Neon 整理 — 統合は可能。ただし今はやらない

### 現状（実測）

`.env` から確認できた Neon エンドポイントは **5つ**（すべて ap-southeast-1）。

| 用途 | エンドポイント（識別子のみ） |
|---|---|
| mvp-booking-system | `ep-wispy-forest-…` |
| mvp-estimate-manager | `ep-floral-surf-…` |
| mvp-lp-generator | `ep-lucky-grass-…` |
| mvp-subscription-ec | `ep-misty-term-…` |
| 2026-project backend | `ep-little-flower-…` |

※ `mvp-freelance-manager` はローカルに `.env` がなく、Vercel 側の環境変数のみで動いている（デモは稼働中）。実際のプロジェクト数は6の可能性がある。

### 判断: **統合は理にかなっているが、実行は後回し**

**統合案**: Neon は1プロジェクト内に複数データベースを持てる。MVP 4〜5本を1プロジェクトに集約すれば、管理対象が1つになり、無料枠（ストレージ・compute時間）の把握も簡単になる。

**それでも今やらない理由**:
1. **移行中にデモが壊れる。** ポートフォリオからリンクしている5本すべてが Neon に依存している
2. Vercel 側の環境変数の張り替えが必要で、**失敗すると本番が落ちる**
3. 就活期間中にサイトのリンクが切れているのが最悪のケース

**推奨タイミング**: **`mvp-booking-system` の改修時にまとめて実施。**
どのみち booking-system はスキーマから作り直すので、そのタイミングで「新しい統合Neonプロジェクトに移す」のが最も安全。他の4本も、v2公開が落ち着いてから1本ずつ移す。

### 今やっておくべきこと

- **Neon のダッシュボードで、実際のプロジェクト数と無料枠の消費状況を確認する**（ストレージ・compute時間）
- 無料枠を圧迫しているものがあれば、その1つだけ先に対処する
- `mvp-freelance-manager` の接続先を把握しておく（ローカルに `.env` がないため、現状Vercel側にしか情報がない）

## 5. 実行順序（確定）

```
1. Phase 2（即効修正）              ← 今すぐ着手可。本人確認不要
2. gin_ec の DBダンプ・.env 除去     ← 個人情報。鍵より優先
3. v2 のリンク構造を確定
4. MVP 5リポジトリの統合 + アーカイブ  ← リンク差し替えと同時
5. 空リポジトリ削除・旧リポジトリのアーカイブ
6. （v2公開後）Neon 統合 ← booking-system 改修と同時
7. （v2公開後）/services の実装
8. （最後）Vercel プロジェクト名の変更
```

**「整理」は壊れると困る作業なので、先に進めるべきは Phase 2。**
逆に、gin_ec の個人情報除去だけは、掲載判断より前に済ませておいて損がない。
